# 관리자 새 운용 시작

관리자 → 회원 관리 → 회원 상세 → **새 운용 시작**에서 확인한 자산을 새로운
운용 기간의 위험 기준으로 기록하고 기존 Worker의 재개 검증을 요청한다.
이 기능을 배포하는 것만으로 계좌가 재개되거나 위험 기준이 변경되지는 않는다.

## 사용자 동작

1. 중지 상태이며 포지션이 없는 회원 계좌를 선택한다.
2. 새 시작 자산, 이전 최고 자산, 기존 손실 한도와 카피 비율을 확인한다.
3. 시작 사유를 입력하고 새 위험 기준 적용에 동의한다.
4. **새 기준으로 재개 요청**을 누른다.
5. Worker가 마스터·회원 미체결, 두 번의 최신 포지션 관측, API 권한 등을
   검사한다. 통과 후에만 ACTIVE가 된다. 화면의 요청 완료는 체결 완료가 아니다.

조회 후 15초가 지났거나 잔액·설정이 변경되면 다시 조회해야 한다. 기존 재개
요청 때문에 계좌 관측이 오래된 경우, 해당 요청이 끝나거나 운영자가 일시중지한
뒤 최신 관측을 확인한다. 중복 응답·재시도는 같은 요청 ID로 원래 결과를 반환한다.

## 보존과 범위

- 과거 거래, 손익, 원래 최고 자산 및 기존 일일 성과 기록을 덮어쓰지 않는다.
- 새 운용 이력에는 관리자, 사유, 시간, 확인한 자산, 이전 위험 기준, 설정,
  재개 세대와 결과 영수증을 남긴다. 감사 기록에도 남긴다.
- 기존 손실 한도·카피 비율을 변경하지 않는다. 새 기간의 최고 자산은 이후
  관측으로 높아지며 실제 손실이 한도에 도달하면 다시 차단한다.
- 새 기간 이후의 계좌 자산 변동은 기존 방식으로 계산한다. 입출금 자동 보정이나
  카피 주문만의 수익률 귀속 기능은 이 변경의 범위가 아니다.
- 일반 재개, 새 입금, 배포, Worker 재시작은 새 운용 기간을 만들지 않는다.
- 회원·비로그인 사용자·Worker는 관리자 실행 API를 호출할 수 없다.

## 검증과 반영

`tests/admin-new-operation.test.js`는 실제 PostgreSQL 함수와 기존 Worker를
합성 계좌로 실행한다. 권한, 최신성, 포지션, 미확정 주문, 설정 변경, 멱등성,
과거 기록 보존, 새 기간 손실 제한과 두 번의 관측 후 활성화를 검증한다.
`tests/fixtures/new-operation-ui.html`은 실제 서비스와 연결되지 않는 UI 검증용이다.

SQL 마이그레이션은 CLI로 생성한 뒤 운영 적용 이력에 맞춰
`20260911062432_admin_new_operation.sql`로 이름을 정렬했다.
기존 계좌에는 별도 운용 기준이 없으므로 Worker context는 기존 값을 사용한다.
운영 적용 전 마이그레이션과 프론트엔드를 검증하며, 대상 계좌의 관리자 확인
버튼은 운영자가 직접 실행한다. main 병합 시 기존 Lightsail 자동 배포가 DRY_RUN으로
전환할 수 있으므로, 프론트엔드와 추가 DB 기능 반영은 Worker 재배포와 구분한다.

## 적용 상태 · 2026-09-11

운영 DB에 추가 기능을 적용했고, 설치 후 운용 이력과 위험 기준 행이 모두 0건임을
확인했다. 전체 Worker는 LIVE이며 기존 계좌의 위험 기준은 유지됐다.
관리자 API는 비로그인 실행을 막고 내부 관리자 확인을 거친다. 새 비공개 테이블은
RLS와 직접 접근 차단을 적용했다. 보안 점검의 관리자 SECURITY DEFINER 안내와
비공개 테이블 정책 없음 안내는 이 접근 모델에 따른 항목이다.

프론트엔드는 PR #45의 미리보기까지 배포됐다. 운영 화면 반영은 Vercel의
Deployments에서 해당 브랜치 배포의 Promote to Production으로 진행할 수 있다.
이는 운영 환경 변수로 프론트엔드를 재빌드하므로 완료 후 관리자 화면을 확인한다.
실제 계좌의 새 운용 시작은 운영자가 직접 확인한다.
